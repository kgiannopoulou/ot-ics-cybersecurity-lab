# Automated red/blue validation

The lab's claims — "the IDS detects an unauthorised client", "the allow-list
stops it", "the interlock contains an overflow" — are checked automatically, so
each scenario ends in **attack → evidence → detection → mitigation**, proven,
not asserted.

Two layers, because they run in different places:

| | Runs | Proves | Needs |
|---|---|---|---|
| [`tests/test_attack_scenarios.py`](../tests/test_attack_scenarios.py) | CI, every push | the **controller-side** defences: recon succeeds, setpoint tampering is reset, the overflow is capped by the interlock | just Python + pymodbus |
| [`tools/validate.py`](../tools/validate.py) | on demand, locally | the **network-side** path: each attack reaches and is detected on the PLC, then is dropped once the host allow-list is applied | the Docker lab running |

## The in-controller tests (CI)

Each attack is run against a real soft-PLC subprocess and the safeguard is
asserted:

```
$ python -m pytest tests/ -q
...........                                                   [100%]
```

| Test | Attack | Expected (blue team) |
|---|---|---|
| `recon_reads_the_full_process_state` | read HR0–5 + coils | succeeds — the exposure monitoring exists for |
| `setpoint_tamper_is_reset_by_input_validation` | write 99 % high setpoint | controller resets it to 80 % (SR 3.5) |
| `overflow_is_contained_by_the_safety_interlock` | shut drain, raise setpoint, force pump | level capped ~95 %, pump forced off |
| `unauthorised_writes_are_accepted_without_a_host_control` | write pump / mode coils | accepted — proves the "before" state is real |

## The live red/blue harness

```sh
docker compose --profile redteam up -d --build     # PLC, HMI, firewall, Suricata, attacker
python tools/validate.py --report detection/evidence/validation-report.md
```

For every scenario the harness:

1. runs the attack from the rogue container (`10.30.30.66`) against the PLC,
2. reads the attack's own JSON result (did it reach the PLC?),
3. checks Suricata's `fast.log` for the lab's SIDs,
4. applies `simulator/plc_allowlist.sh on` (only the HMI may reach TCP 502),
5. re-runs the attack and asserts it is now **blocked**,
6. restores the baseline (`allow-list off`).

It exits non-zero unless every scenario shows the expected transition.

### Last result

See [`detection/evidence/validation-report.md`](../detection/evidence/validation-report.md),
regenerated by the command above. Summary:

| Scenario | Reached PLC (before) | Suricata SIDs | Blocked (after allow-list) |
|---|---|---|---|
| recon | ✅ | 9000001 | ✅ |
| sweep | ✅ | 9000009 (tap-dependent)¹ | ✅ |
| setpoint | ✅ | 9000001 / 9000003 | ✅ |
| pump | ✅ | 9000001 / 9000003 / 9000005 | ✅ |
| mode | ✅ | 9000001 / 9000003 / 9000013 | ✅ |

¹ The IDS taps only the PLC interface, so it sees one probe to the PLC, below
the 5-SYN sweep threshold; a subnet-wide sweep needs a span port on the OT
switch. The single probe is still dropped by the allow-list.

Every unauthorised client trips the catch-all **9000001** (any non-HMI Modbus)
and every unauthorised write trips **9000003**, so detection does not depend on
the exact function code; the function-specific SIDs (9000004/5/13) add the
"what was touched" detail.

## What this closes

Scenario 03 (process manipulation) previously said *"live execution left for the
VM build"*. The write and overflow paths now execute for real against the Docker
lab on every validation run, and the controller-side containment runs in CI, so
the kill-chain is demonstrated end to end rather than only rule-tested.
